# Общие договорённости

Долговременная память проекта между задачами. `TZ.md` — что строим и зачем, GitHub issues — отдельные задачи (решения по конкретной фиче — в тексте issue), `design/garage.pen` — как выглядит UI, а этот файл — общие правила, ловушки и контракты, которые одна задача создаёт, а следующие используют.

Правила ведения:

- Разделы **«Решения»** и **«Контракты»** обновляются в том же коммите, где решение принято или контракт создан. Формат строки: `- (#N) что решили / что создали — путь, сигнатура`.
- Только то, что понадобится следующим задачам. Пересказ сделанного — в коммитах и PR, не здесь.
- Если решение меняется — исправить строку, а не дописывать противоречащую.
- Файл держать коротким: его целиком читает каждая итерация Ralph loop.

## Критерии завершения задачи

Задача завершена, только если реализация соответствует issue и `TZ.md`, на новое/изменённое поведение написаны тесты, а `npm test`, `npm run typecheck`, `npm run build` и `npm run test:e2e` проходят. Задача с UI дополнительно имеет e2e-сценарий на Playwright со скриншотами затронутых экранов.

## Тесты

- Корневой `vitest.config.ts` собирает три проекта, у каждого свой `vitest.config.ts`: `apps/api` (node: `tests/unit`, `tests/server`, `tests/integration`), `apps/web` (happy-dom: `tests/**`, клиентские утилиты вроде `apiClient`) и `packages/shared` (node: Zod-схемы и чистые утилиты).
- `apps/api/tests/server/` — прямой импорт `server/utils/*.ts` (`access.ts`, `push.ts`) на временной SQLite (`tests/helpers/testDb.ts`: файл в `os.tmpdir()`, миграции из `server/database/migrations`, сид одной категории). Старые утилиты написаны в расчёте на авто-импорты Nitro (`createError` и т.п.), поэтому `tests/setup/node-globals.ts` кладёт `createError` из `h3` в `globalThis`. Новые утилиты писать с явными импортами и конфигом в аргументах (как `tokens.ts`) — их проще тестировать. `server/database/index.ts` открывает соединение по `DB_FILE_NAME` в момент импорта — в тестах сначала выставить `process.env.DB_FILE_NAME`, затем `await import('../../server/database')` (динамически, не статическим import).
- `apps/api/tests/integration/` — API-роуты (`server/api/**`) нельзя импортировать напрямую: они используют авто-импорты Nitro и `useRuntimeConfig`. Поэтому тестируются по HTTP на реальном сервере: globalSetup `tests/setup/buildApi.ts` один раз собирает API (`nitropack build` программно) в `os.tmpdir()/garage-api-test-<хэш worktree>` и пересобирает, только если изменились `server/`, `nitro.config.ts`, `package.json` или `packages/shared` (иначе берёт кэш); `tests/helpers/apiServer.ts` `startApiServer(env)` запускает готовый `server/index.mjs` на своём порту с переданным окружением (`NUXT_*` читаются при старте), `createHttpClient(baseUrl)` → `fetch`/`$fetch`. Каждый тест-файл — свой сервер и своя БД, файлы идут параллельно. Ловушки: сервер слушает `127.0.0.1` (Node на этой машине получает EACCES при подключении к `::1`); `nitropack dev` в тестах не использовать — он компилирует сервер при каждом старте (~12 с на файл) и параллельные экземпляры конфликтуют за `.nitro`.
- Сессия — стейтлес подписанная кука без серверного хранилища: старая кука остаётся валидной, даже если ей уже прислали logout. Тест на logout должен переслать именно ту (уже просроченную) куку, которую вернул сам ответ `/api/auth/logout`. Bearer-режим, наоборот, проверяется на сервере: refresh-токены лежат в `refresh_tokens` и отзываются.
- Web-push мокается через `vi.mock('web-push', ...)` + `globalThis.useRuntimeConfig = () => ({...})` (единственный авто-импорт, которым пользуется `server/utils/push.ts`); `db`/`schema` — обычные импорты, стабить не нужно.
- `computeNextDue` живёт в `packages/shared/utils/reminderDue.ts` (сервер и клиент импортируют оттуда) и считает даты в UTC (`addMonths`), от часового пояса не зависит. `getReminderStatus`/`todayIso` зависят от TZ — тесты дат фиксируют `TZ=UTC` (сделано в каждом `vitest.config.ts` и в `env` запускаемого сервера).

## БД и API

- (#46) Категории принадлежат машине: `categories.carId` (FK на `cars`, cascade); `carId = null` — стандартная (сид, `isDefault: true`), иначе своя категория этой машины. Уникальность: `(carId, name)` и отдельный частичный индекс имён стандартных (`WHERE car_id IS NULL` — SQLite считает NULL разными, без него сид при каждом старте контейнера плодил бы дубли). Имя своей категории может совпадать со стандартной — проверять в роутах, если нужно. `Category.carId: number | null` в `@garage/shared/types`. Миграция `0003_car_categories` перенесла старые глобальные свои категории: одна машина → привязана, несколько → копия на каждую (записи и напоминания переназначены), не используется → удалена. Ручная SQL-часть в `.sql` миграции разрешена, но drizzle-kit теряет `ON DELETE` у `ADD COLUMN ... REFERENCES` — сверять сгенерированный SQL. Тест миграций по старой схеме — `apps/api/tests/server/categoriesMigration.test.ts` (обрезанный `_journal.json`).
- (#47) Категории машины: `GET /api/cars/[id]/categories` → `Array<Category & { entriesCount }>` (стандартные + свои этой машины, по имени; счётчик — записи этой машины), `POST` `{ name }` — любой участник, 409 если имя занято среди стандартных и своих (`categoryNameTaken` в `server/utils/categories.ts`; на разных машинах имена могут совпадать), ответ с `entriesCount: 0`. `PATCH`/`DELETE /api/categories/[id]` — своя категория по доступу к её машине (`requireOwnCategory`), стандартная → 403, нет → 404. Удаление в транзакции: записи → стандартная «Прочее» (`FALLBACK_CATEGORY_NAME`; нет её — `null`), `reminders.categoryId` → `null`. Глобальные `/api/categories` (GET/POST) удалены; клиент — `useCategories(carId)` (кэш по машинам, `fetchCategories(force?)`, тип `CarCategory`), устаревший `EntryForm.vue` без использований удалён. `categorySchema.name` — trim, ≤ 40 символов. Состояние модульное (SPA, без `useState`), выводит его единственный `<UiToast />` в `app.vue` (live-регион `role=status` есть всегда). Отступ снизу — CSS-переменная `--toast-bottom` (по умолчанию `--sp-4`) + safe-area: layout с нижней панелью задаёт её, чтобы toast стоял над TabBar. В e2e перед `snap()` держать toast `dispatchEvent('pointerdown')`.
- (#38) `UiAlert` — встроенное сообщение в потоке экрана (не успех после действия — это toast): `variant: 'error'|'warning'|'success'|'info'`, `title`, `message` | слот, `icon?` (замена иконки варианта: `WifiOff`, `PartyPopper`), слот `actions` — кнопки под текстом (Е3). `error` → `role=alert`, остальные — `status`. `UiEmptyState` — `icon`, `title` (h2), `message?`, `tone: 'neutral'|'danger'` (ошибка загрузки, В6), одно действие — слот `action` (`UiButton`; нет слота — нет кнопки); в списке — внутри `UiCard`. `UiReminderBridge` — «мостик» запись → напоминание (Д2): `title` («Закрыть «Замена масла»»), `subtitle?`, `v-model: boolean` (по умолчанию `true`), выключен — нейтральный фон. `UiDisclosure` — `label`, `v-model:open` (по умолчанию закрыт), слот — свёрнутые поля; закрытое содержимое не рендерится (не попадает в Tab и форму — значения держит родитель). Высота 0 → auto и обратно — `<Transition name="collapse" v-on="collapseTransitionHooks">` (`utils/collapseTransition.ts`), переиспользовать для офлайн-плашки. Витрина — группа `feedback` (`components/dev/ShowcaseFeedback.vue`), e2e `snap('ui-toast')`, `snap('ui-feedback')`.
- (#38) Навигация: `UiAppBar` — `variant: 'car'|'back'`, положение (sticky/fixed) задаёт layout, сверху safe-area. `car`: `carName`, `plateNumber?` (`UiPlate`), `userName` (аватар), `profileTo = '/profile'`; название + номер — одна кнопка «Сменить машину: …» (`aria-haspopup=dialog`) → `switch`; слот `action` заменяет аватар. `back`: `title` (h1), `backTo?` (ссылка, иначе эмитит `back`), слот `action` справа («Готово» — `UiButton variant="text" size="sm"`). `UiTabBar` — `carId`, `active?: CarTab | null`, `badge?` (просрочено + скоро; 0 → нет счётчика, есть sr-only «требуют внимания: N»), эмитит `add` («＋», кнопка «Добавить запись»); вкладки — ссылки `carTabPath(carId, tab)` с `aria-current=page`. `CarTab = 'overview'|'journal'|'reminders'|'expenses'`, `carTabPath` → `/cars/7` | `/cars/7/journal` (`utils/carTabs.ts`).
