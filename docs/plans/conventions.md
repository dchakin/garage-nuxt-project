# Общие договорённости

Долговременная память проекта между задачами. `TZ.md` — что строим и зачем, GitHub issues — отдельные задачи (решения по конкретной фиче — в тексте issue), `design/garage.pen` — как выглядит UI, а этот файл — общие правила, ловушки и контракты, которые одна задача создаёт, а следующие используют.

Правила ведения:

- Разделы **«Решения»** и **«Контракты»** обновляются в том же коммите, где решение принято или контракт создан. Формат строки: `- (#N) что решили / что создали — путь, сигнатура`.
- Только то, что понадобится следующим задачам. Пересказ сделанного — в коммитах и PR, не здесь.
- Если решение меняется — исправить строку, а не дописывать противоречащую.
- Файл держать коротким: его целиком читает каждая итерация Ralph loop.

## Критерии завершения задачи

Задача завершена, только если реализация соответствует issue и `TZ.md`, на новое/изменённое поведение написаны тесты, а `npm test`, `npm run typecheck`, `npm run build` и `npm run test:e2e` проходят. Задача с UI дополнительно имеет e2e-сценарий на Playwright со скриншотами затронутых экранов.

## Тесты

- Корневой `vitest.config.ts` собирает три проекта, у каждого свой `vitest.config.ts`: `apps/api` (node: `tests/unit`, `tests/server`, `tests/integration`), `apps/web` (happy-dom: `tests/**`, клиентские утилиты вроде `apiClient`) и `packages/shared` (node: Zod-схемы и чистые утилиты).
- `apps/api/tests/server/` — прямой импорт `server/utils/*.ts` (`access.ts`, `push.ts`) на временной SQLite (`tests/helpers/testDb.ts`: файл в `os.tmpdir()`, миграции из `server/database/migrations`, сид одной категории). Старые утилиты написаны в расчёте на авто-импорты Nitro (`createError` и т.п.), поэтому `tests/setup/node-globals.ts` кладёт `createError` из `h3` в `globalThis`. Новые утилиты писать с явными импортами и конфигом в аргументах (как `tokens.ts`) — их проще тестировать. `server/database/index.ts` открывает соединение по `DB_FILE_NAME` в момент импорта — в тестах сначала выставить `process.env.DB_FILE_NAME`, затем `await import('../../server/database')` (динамически, не статическим import).
- `apps/api/tests/integration/` — API-роуты (`server/api/**`) нельзя импортировать напрямую: они используют авто-импорты Nitro и `useRuntimeConfig`. Поэтому тестируются по HTTP на реальном сервере: globalSetup `tests/setup/buildApi.ts` один раз собирает API (`nitropack build` программно) в `os.tmpdir()/garage-api-test-<хэш worktree>` и пересобирает, только если изменились `server/`, `nitro.config.ts`, `package.json` или `packages/shared` (иначе берёт кэш); `tests/helpers/apiServer.ts` `startApiServer(env)` запускает готовый `server/index.mjs` на своём порту с переданным окружением (`NUXT_*` читаются при старте), `createHttpClient(baseUrl)` → `fetch`/`$fetch`. Каждый тест-файл — свой сервер и своя БД, файлы идут параллельно. Ловушки: сервер слушает `127.0.0.1` (Node на этой машине получает EACCES при подключении к `::1`); сборка во временном каталоге не видит корневой `node_modules` (Nitro оставляет в `output/server/node_modules` лишь заглушки `package.json`), поэтому `buildApi.ts` `linkDependencies` подставляет junction на него — иначе каждый роут с `drizzle-orm` отвечает 500 (`ERR_MODULE_NOT_FOUND`; отладка — `API_SERVER_DEBUG=1`); `nitropack dev` в тестах не использовать — он компилирует сервер при каждом старте (~12 с на файл) и параллельные экземпляры конфликтуют за `.nitro`.
- Сессия — стейтлес подписанная кука без серверного хранилища: старая кука остаётся валидной, даже если ей уже прислали logout. Тест на logout должен переслать именно ту (уже просроченную) куку, которую вернул сам ответ `/api/auth/logout`. Bearer-режим, наоборот, проверяется на сервере: refresh-токены лежат в `refresh_tokens` и отзываются.
- Web-push мокается через `vi.mock('web-push', ...)` + `globalThis.useRuntimeConfig = () => ({...})` (единственный авто-импорт, которым пользуется `server/utils/push.ts`); `db`/`schema` — обычные импорты, стабить не нужно.
- `computeNextDue` живёт в `packages/shared/utils/reminderDue.ts` (сервер и клиент импортируют оттуда) и считает даты в UTC (`addMonths`), от часового пояса не зависит. `getReminderStatus`/`todayIso` зависят от TZ — тесты дат фиксируют `TZ=UTC` (сделано в каждом `vitest.config.ts` и в `env` запускаемого сервера).

## БД и API

- (#46) Категории принадлежат машине: `categories.carId` (FK на `cars`, cascade); `carId = null` — стандартная (сид, `isDefault: true`), иначе своя категория этой машины. Уникальность: `(carId, name)` и отдельный частичный индекс имён стандартных (`WHERE car_id IS NULL` — SQLite считает NULL разными, без него сид при каждом старте контейнера плодил бы дубли). Имя своей категории может совпадать со стандартной — проверять в роутах, если нужно. `Category.carId: number | null` в `@garage/shared/types`. Миграция `0003_car_categories` перенесла старые глобальные свои категории: одна машина → привязана, несколько → копия на каждую (записи и напоминания переназначены), не используется → удалена. Ручная SQL-часть в `.sql` миграции разрешена, но drizzle-kit теряет `ON DELETE` у `ADD COLUMN ... REFERENCES` — сверять сгенерированный SQL. Тест миграций по старой схеме — `apps/api/tests/server/categoriesMigration.test.ts` (обрезанный `_journal.json`).
