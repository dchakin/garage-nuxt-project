# Техническое задание

## Приложение учёта обслуживания и трат на автомобиль

Версия: 1.0
Дата: 09.07.2026

---

## 1. Назначение и цель

Пет-проект для замены Google-таблицы, в которой сейчас ведётся учёт того, что и когда чинилось, менялось и покупалось для автомобиля. Цель — удобный веб-инструмент для бытового использования: журнал событий по машине, напоминания о плановом ТО и простая аналитика трат.

Данные из текущей таблицы не переносятся — старт с чистой базы.

## 2. Пользователи

- Владелец (сам пользователь) — полный доступ, управление автомобилями и участниками.
- Члены семьи/друзья — доступ к общим автомобилям по приглашению, могут добавлять и просматривать записи.

Нужна авторизация с разграничением доступа: пользователь видит только те автомобили, к которым имеет доступ (владелец или приглашённый участник).

## 3. Функциональность MVP

### 3.1 Автомобили

- CRUD автомобиля: марка, модель, год, гос. номер, VIN (опционально), пробег на текущий момент, фото (опционально).
- Список автомобилей пользователя с быстрым переключением между ними.
- Добавление других пользователей к автомобилю по email с ролью «участник» (может добавлять записи и напоминания, обновлять пробег) — без сложной ролевой матрицы на первом этапе. Участник добавляется сразу, без приглашения и подтверждения; человек должен быть уже зарегистрирован. Владелец может убрать участника, участник — сам покинуть машину.
- Пробег обновляется отдельно от записи (владелец и участники). Уменьшить пробег можно только после явного подтверждения — на случай опечатки при прошлом вводе.

### 3.2 Журнал событий (записи)

Основная сущность — запись о событии, привязанная к автомобилю. Поля:

- Дата события.
- Тип: ремонт, замена расходника, покупка, плановое ТО, прочее.
- Категория (например: двигатель, тормоза, шины, масло, кузов, электрика). Стандартные категории общие для всех машин и не меняются; свои категории принадлежат машине, их можно добавить, переименовать и удалить (записи удалённой переходят в «Прочее»).
- Описание (текст).
- Пробег на момент события.
- Стоимость (сумма, валюта — по умолчанию одна валюта на аккаунт).
- Место (сервис/магазин), опционально.
- Вложения — фото чека или детали (опционально в MVP, если позволит время).

Операции: создание, просмотр списка (с сортировкой по дате/пробегу), просмотр карточки записи, редактирование, удаление. Фильтрация списка по автомобилю, типу, категории, диапазону дат.

### 3.3 Напоминания

- Создание напоминания, привязанного к типу работ (например «замена масла»), с условием срабатывания: по дате (конкретная дата или интервал в месяцах от последней замены) и/или по пробегу (интервал в км от последнего значения).
- Возможность связать напоминание с последней подходящей записью в журнале, чтобы система сама предлагала следующую дату/пробег.
- Список активных напоминаний с индикацией статуса: скоро, просрочено, ок.
- Уведомление в интерфейсе (баннер/бейдж) при входе в приложение.
- Web Push-уведомления (через PWA): раз в день, после добавления записи с пробегом и после обновления пробега — о напоминаниях, перешедших в статус «скоро»/«просрочено»; каждое уведомление по одному сроку отправляется один раз. Выключенные напоминания push не шлют и в счётчике не учитываются. Закрытие напоминания записью («Сделал») пересчитывает срок, и push по новому сроку уходит снова. Email-уведомления — вне рамок.

### 3.5 Аккаунт

- Профиль: имя (можно изменить), email (только чтение), смена пароля по текущему паролю.
- Восстановление пароля по email: одноразовая ссылка на 1 час, после сброса старые сессии недействительны. Это единственное, для чего приложение отправляет почту; без настроенной почты функция выключена.
- Удаление аккаунта: удаляются машины, где пользователь владелец, со всеми записями и напоминаниями; из чужих машин он выходит.

### 3.6 Отступления от первой версии ТЗ

Приняты при редизайне (`docs/prd-implement-redesign-from-garage-pen.md`, фрейм «08 · UX-аудит» в `design/garage.pen`):

1. Пробег можно уменьшить — только после явного подтверждения.
2. Восстановление пароля по email (исключение из «email вне рамок»).
3. Участник добавляется сразу, без приглашения.
4. Свои категории принадлежат машине; их можно переименовывать и удалять.
5. Удаление аккаунта.

### 3.4 Аналитика

- Дашборд по автомобилю: сумма трат за период (месяц/квартал/год/всё время), разбивка по категориям (диаграмма), динамика трат по месяцам (график).
- Простая сводка: сколько потрачено всего, средний чек, самая затратная категория.

## 4. Нефункциональные требования

- Адаптивная вёрстка (мобильный — основной сценарий использования, вносить данные часто удобнее с телефона).
- Русский язык интерфейса.
- Время отклика API — не критично для пет-проекта, но CRUD-операции не должны ощутимо тормозить (это не масштабный сервис).
- Хранение данных — надёжность на уровне «не потерять данные при обычной эксплуатации» (регулярный бэкап файла БД).
- Код на TypeScript со строгой типизацией, без `any` в бизнес-логике.

## 5. Технологический стек

- Фронтенд (`apps/web`): Nuxt 3 в режиме SPA (`ssr: false`, сборка `nuxt generate`), TypeScript, Vue 3 (Composition API), Tailwind CSS — для стилей (быстро для пет-проекта).
- Бэкенд (`apps/api`): отдельное приложение на Nitro (`server/api/**`) без Nuxt. Клиент и API разделены (npm workspaces: `apps/web`, `apps/api`, `packages/shared`), чтобы тот же клиент можно было упаковать в мобильные приложения (`docs/plans/mobile-stores.md`).
- База данных: SQLite (файл), доступ через Drizzle ORM (типобезопасные запросы, миграции, хорошо сочетается с TS и Nitro).
- Авторизация: email+пароль; веб — подписанная httpOnly-кука (h3 `useSession`), мобильный клиент — access-токен (JWT, 15 мин) + одноразовый refresh-токен (`Authorization: Bearer`). Не требует внешних сервисов, подходит для пет-проекта с небольшим числом пользователей.
- Валидация данных: Zod — на входе API-роутов.
- Графики: `chart.js` + `vue-chartjs` (или `unovis`) для аналитики.
- Деплой: контейнер/VPS или сервисы вроде Fly.io/Railway с поддержкой персистентного диска для файла SQLite; либо Vercel/Netlify с внешней БД (Turso — SQLite-совместимая) — решается на этапе деплоя.

## 6. Модель данных (основные сущности)

- **User**: id, email, password_hash (или auth-провайдер), name, created_at.
- **Car**: id, owner_id (User), brand, model, year, plate_number, vin, current_mileage, photo_url, created_at.
- **CarMember**: id, car_id, user_id, role (owner/member), invited_at.
- **Category**: id, car_id (null — стандартная, общая для всех машин), name, is_default.
- **PasswordResetToken**: id, user_id, token_hash, expires_at, used_at (сброс пароля; плюс `users.session_version`, чтобы сброс обнулял старые сессии). У Car есть ещё `mileage_updated_at`.
- **Entry** (запись журнала): id, car_id, author_id (User), date, type (repair/replacement/purchase/maintenance/other), category_id, description, mileage, cost, currency, place, created_at.
- **EntryAttachment** (опционально в MVP): id, entry_id, file_url.
- **Reminder**: id, car_id, title, category_id, trigger_type (date/mileage/both), interval_months, interval_km, last_entry_id (nullable, ссылка на Entry, от которой считать), next_due_date, next_due_mileage, is_active, created_at.

## 7. Основные API-роуты (Nitro, `apps/api/server/api`)

- `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/session`, `POST /api/auth/refresh` (обмен refresh-токена на новую пару; login/register принимают `authMode: 'token'` для мобильного клиента).
- `PATCH /api/auth/me` — имя, `POST /api/auth/password` — смена пароля, `DELETE /api/auth/account` — удаление аккаунта.
- `GET /api/auth/config` — включён ли сброс пароля; `POST /api/auth/password-reset` — письмо со ссылкой, `POST /api/auth/password-reset/confirm` — новый пароль по токену и вход.
- `GET/POST /api/cars`, `GET/PATCH/DELETE /api/cars/[id]`; `PATCH /api/cars/[id]/mileage` — обновить пробег (любой участник, уменьшение — с `confirmDecrease`).
- `POST /api/cars/[id]/invite` — добавить участника по email; `DELETE /api/cars/[id]/members/[userId]` — убрать участника (владелец), `DELETE /api/cars/[id]/members/me` — покинуть машину.
- `GET/POST /api/cars/[id]/entries` (POST принимает `reminderId` — закрыть напоминание записью), `GET/PATCH/DELETE /api/entries/[id]`.
- `GET/POST /api/cars/[id]/reminders`, `POST /api/cars/[id]/reminders/bulk` (мастер первого запуска), `GET/PATCH/DELETE /api/reminders/[id]`.
- `GET /api/cars/[id]/analytics?period=month|year|all&date=…` — итоги, средние, ряды по месяцам и категориям, соседние периоды с тратами.
- `GET/POST /api/cars/[id]/categories` — стандартные и свои категории машины; `PATCH/DELETE /api/categories/[id]` — только свои (стандартные — 403).
- `GET /api/push/config`, `POST/DELETE /api/push/subscribe`, `POST /api/push/test` — Web Push.

Все роуты, кроме auth и push-конфига, проверяют, что пользователь — владелец или участник соответствующего автомобиля.

## 8. Экраны (UI)

Макет — `design/garage.pen` (коды экранов А1–И10, тёмная тема Т1–Т8, сценарии 1–5).

1. Вход, регистрация, восстановление пароля (А1–А3, А7–А9) и мастер первого запуска: машина → что напоминать (А4–А6).
2. Экраны машины с нижней панелью «Обзор · Журнал · ＋ · Напоминания · Расходы» и переключателем машин в шапке (Б4); открывается последняя машина.
3. «Обзор»: пробег с обновлением (Б5–Б7), «Требует внимания», расходы месяца, последние записи (Б1–Б3).
4. «Журнал»: записи по месяцам с суммами, фильтр по типу, поиск, сортировка (В1–В7); шторки новой записи и просмотра/правки (Д1–Д4) открываются с любого экрана машины.
5. «Напоминания»: группы по статусам, «Сделал», шторки создания из шаблона и правки (Г1–Г3, Е1–Е4).
6. «Расходы»: период «Месяц / Год / Всё время», итоги, графики по месяцам и категориям (Ж1–Ж3).
7. Настройки автомобиля: данные авто, пробег, категории, участники; вид участника (З2–З4, И1, И2, И8, И9).
8. Профиль: push, тема, машины, аккаунт (З1, И10); экраны 403/404/500/«Сессия истекла» (И4–И7).

## 10. Этапы разработки

1. **Каркас**: инициализация Nuxt-проекта, TS, Tailwind, Drizzle + SQLite, авторизация, базовые модели User/Car.
2. **Журнал**: CRUD автомобилей и записей, фильтрация, UI списка и формы.
3. **Напоминания**: логика вычисления «когда менять», UI списка и статусов.
4. **Аналитика**: агрегирующий API-роут, графики на дашборде.
5. **Мультипользовательность**: приглашение участников, разграничение доступа.
6. **Полировка**: адаптивность под мобильные, обработка ошибок, пустые состояния, деплой.
